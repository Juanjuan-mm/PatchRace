# Decision Log

Last updated: 2026-07-23

Statuses: `PROPOSED`, `ACCEPTED`, `SUPERSEDED`, `REJECTED`.

M0 product decisions were accepted on 2026-07-22 under the user's instruction to execute the full milestone. Implementation-stack details that require M1 spikes remain proposed.

| ID | Status | Decision | Rationale | Revisit trigger |
|---|---|---|---|---|
| `ADR-001` | ACCEPTED | Build Pi-native but not Pi-only. | Pi is the optimization target and reference harness; Claude Code and Codex expand demand and provide comparative evidence. | Cross-agent adapters prove legally, technically, or operationally infeasible. |
| `ADR-002` | ACCEPTED | Make the closed loop the primary story: race → diagnose → propose → validate → promote. | Comparison alone is increasingly commoditized; evidence-backed Pi improvement creates a user outcome and stronger narrative. | Users want comparison but do not repeat the teaching workflow in beta. |
| `ADR-003` | ACCEPTED | Remain local-first for v0.1. | Source, prompts, traces, credentials, and evaluation artifacts are sensitive; local CLI also reduces adoption friction. | A required launch workflow cannot operate locally. |
| `ADR-004` | ACCEPTED | Deterministic correctness gates precede LLM judgment. | LLM judges cannot rescue failing tests and should not obscure objective regressions. | A task domain lacks executable verification; such support would require explicit methodology. |
| `ADR-005` | ACCEPTED | Analyze observable trajectories, not hidden reasoning. | File/tool/command/edit/test evidence is user-visible, auditable, and sufficient for workflow diagnosis without seeking chain-of-thought. | None expected; this is a product and ethical boundary. |
| `ADR-006` | ACCEPTED | Validate candidates with train/validation/final holdout separation. | Generated Skills and instructions often fail or overfit; final evidence must come from unseen tasks. | Task count is too small, in which case the product must downgrade claims to diagnostic only. |
| `ADR-007` | ACCEPTED | Stage project-local Pi artifacts and require explicit promotion. | Prevents silent corruption of personal/global Pi configuration and makes changes reviewable and reversible. | A future opt-in automation mode is designed with equivalent safety and evidence gates. |
| `ADR-008` | ACCEPTED | Do not auto-generate or activate executable Pi Extensions in v0.1. | Extensions carry materially greater security and reliability risk than Markdown configuration/skills/prompts. | Hardened sandbox and executable-artifact review exist after launch. |
| `ADR-009` | ACCEPTED | Use a strict ESM TypeScript 6 / Node 22-and-24-LTS core, pnpm workspaces, and npm distribution. | All M1 spikes worked with Node primitives and Pi's Node SDK; one required runtime minimizes install and adapter friction. | Supported LTS lines, Pi SDK, or a critical library becomes incompatible. |
| `ADR-010` | ACCEPTED | Use `PatchRace` as the development name and recheck/reserve at launch. | Point-in-time GitHub/npm/domain/trademark discovery found no blocking exact collision; the name preserves the broad comparison surface while supporting the Pi-specific hook. | Namespace becomes unavailable, legal review objects, or user research strongly prefers another name. |
| `ADR-011` | ACCEPTED | License PatchRace under Apache-2.0. | Permissive adoption plus explicit patent terms fit an extensible agent-tooling ecosystem. | Governance, ownership, or dependency constraints require another license before first publication. |
| `ADR-012` | ACCEPTED | Keep optimizer engines pluggable; ship a bounded built-in loop first. | Avoids heavy Python/install friction while leaving room for GEPA/EvoSkill integration after the core product works. | Built-in mutation search is demonstrably inadequate before beta. |
| `ADR-013` | ACCEPTED | Use a lead-maintainer governance model, DCO 1.1, and Contributor Covenant 2.1. | Low initial process overhead with explicit contribution rights, accountability, moderation, and a path to multi-maintainer review. | A second maintainer, legal entity, commercial service, major contributor requirement, or governance incident. |
| `ADR-014` | ACCEPTED | Ship v0.1 with no automatic PatchRace telemetry or artifact upload. | Private code, prompts, traces, and local paths make opt-out collection an unacceptable default for the first release. | A later accepted telemetry ADR specifies exact data, purpose, retention, and default-off tests. |
| `ADR-015` | ACCEPTED | Qualify improvement claims by evidence tiers and enforce explicit stop/pivot criteria. | Small samples and repeated holdout use can make self-improvement claims misleading; product continuation must be tied to activation, cost, safety, and held-out evidence. | Pre-release evidence supports a stricter statistically grounded policy. |
| `ADR-016` | ACCEPTED | Treat worktrees as repository-isolation tools, never as a security sandbox. | Agent and repository processes still inherit host permissions, credentials, filesystem, and network access. | A separately verified sandbox backend is introduced and claims are scoped to it. |
| `ADR-017` | ACCEPTED | Integrate Pi through its current `@earendil-works/pi-coding-agent` SDK plus JSON CLI fallback; use Claude Code print stream-json and Codex exec JSONL. | M1 proved these official structured surfaces, event/session capture, and cancellation; the former Pi namespace is deprecated. | An official surface is removed, becomes unstable across supported versions, or a stronger stable protocol replaces it. |
| `ADR-018` | ACCEPTED | Ship a dependency-light standalone report with stable JSON and vanilla TypeScript/CSS rather than a UI framework or server. | v0.1 needs local auditable reports, not a daemon; this minimizes package size, active-content risk, and release surface. | Report scale/accessibility cannot meet product gates without a framework. |
| `ADR-019` | ACCEPTED | Keep Python optional and out-of-process; no Python runtime is required for v0.1. | No M1 feasibility requirement needed Python; optimizer bridges can use a bounded JSONL subprocess later. | A release-critical grader or optimizer has no viable Node implementation. |
| `ADR-020` | ACCEPTED | Resolve adapters by executable health/version/auth probes, not PATH presence, and fail explicitly on unavailable auth. | M1 found a broken PATH Codex package and an installed but unauthenticated Claude CLI; silent fallback would corrupt provenance. | Official CLI discovery/version APIs provide a stronger authenticated registry. |
| `ADR-021` | ACCEPTED | Use explicitly confirmed, fully redacted OpenTelemetry OTLP/JSON `resourceSpans` as the optional v0.1 standard trace export. | OTLP/JSON is portable and dependency-free; PatchRace can preserve event order and unavailable timestamps without adding an uploader or pretending vendor parity. | A launch integration requires another public format or OpenTelemetry changes its stable JSON mapping. |
| `ADR-022` | ACCEPTED | Publish a source-only `v0.1.0-rc.1` GitHub preview before independent-user beta, with the beta gate explicitly waived rather than reported as passed. | The owner directed the project to skip pre-publication participant recruitment, publish the working system on GitHub, and use it personally before requesting follow-up fixes. The deterministic dogfood, correctness, safety, privacy, documentation, package-content, and release-candidate gates remain mandatory. | Five independent target users complete the existing beta protocol; owner testing finds a release blocker; or the project prepares a stable/npm release. |
